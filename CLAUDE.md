# Contribution Guide — ix-recipes

ix-recipes holds the domain skills and the workflows built on top of
[ix-skills](https://github.com/amiel-35/ix-skills). ix-skills holds the cognitive
atoms (gestures that apply to any content); ix-recipes holds what needs domain
knowledge or produces an artefact a profession defines.

## 1. Repo structure

| Path | Role |
|---|---|
| `skills/` | Canonical source: one `.md` file per skill + `.mystaffy.json` override files |
| `dist/` | Plugin root: `.claude-plugin/plugin.json` + `skills/<id>/SKILL.md` — **committed**, skills generated by `build.py` |
| `mystaffy-dist/`, `codex-dist/` | Generated by `build.py` — gitignored |
| `.claude-plugin/marketplace.json` | Marketplace manifest, points at `./dist` |
| `build.py` | Packaging entry point — **a copy of ix-skills' `build.py`** (see §7) |
| `THIRD_PARTY.md` | Every public source a skill draws on, with its licence |

## 2. The dependency rule

**ix-recipes depends on ix-skills, never the other way round.**

- A skill here may point to an ix-skills atom (`see \`decision\``).
- An ix-skills atom must never point to a skill here: a user may have ix-skills
  without ix-recipes.
- Skill ids must stay unique across both repos (Codex installs them flat into
  `~/.codex/skills/`, a collision overwrites). Check ix-skills before naming a skill.

Placement test for a new skill: does it rely on domain knowledge that can be wrong
or out of date (law, HR practice, finance, product methods), or produce an artefact
a profession defines? Then it belongs here. If it applies a reasoning gesture to
any content, it belongs in ix-skills.

## 3. Canonical skill format

Same as ix-skills. Each `skills/<id>.md` file starts with a YAML frontmatter block.

Required: `id` (kebab-case, matches the filename), `label` (French), `version`
(semver), `description_fr`, `description_en`, `icon`, `domain` (§6),
`input_types`, `output_types`, `compatible`
(`[claude-ai, claude-code, cowork, gpt, gemini, mystaffy]`).
Optional: `category` (mystaffy atom type), `aliases`.

The body is written **entirely in English**.

Corpus convention: a skill with nothing to produce opens with « RAS — » followed
by the reason, and stops.

## 4. Workflows

A workflow chains ix-skills atoms for a recurring job (first candidates:
`note-strategique` → `decision` then `deliver`; `offer-comparison` →
`vendor-scorecard` then `decision`). **The format is not settled yet** — to be
designed and tested on a prototype before writing more. Open points: a
`requires` field listing the ix-skills ids, checked by `build.py`; portability,
since Claude Code / Cowork can invoke another skill but ChatGPT / Gemini cannot be
relied on to.

## 5. Checklist — adding a new skill

1. Check the placement test (§2) and that the id is free in ix-skills
2. Create `skills/<id>.md` with complete canonical frontmatter, body in English
3. Create `skills/<id>.mystaffy.json` with `category`, `params`, `ui` (minimum)
4. If anything is taken from another repo or document: check its licence, add it to `THIRD_PARTY.md` in the same commit
5. `python3 build.py <id> --validate`, then `python3 build.py <id>` — commit the regenerated `dist/skills/<id>/SKILL.md`

## 7. Packaging

Targets and commands are the same as ix-skills (`agentskills`, `cowork`,
`mystaffy`, `ix-memory`, `codex`).

```bash
python3 build.py                        # all targets, all skills
python3 build.py --target agentskills   # dist/skills/<id>/SKILL.md
python3 build.py --validate             # validate without writing
claude plugin validate dist
bash scripts/install-codex.sh           # build + install into ~/.codex/skills/
```

- `dist/` is the plugin root in the **default** `skills/<id>/SKILL.md` layout, with no
  custom `skills` field in `plugin.json`: the Cowork / claude.ai validator is stricter
  than the CLI. Do not move the plugin to the repo root.
- `dist/` is committed: plugin installs read the repo as checked out from git. Rebuild
  and commit `dist/` with every skill change. `dist/.claude-plugin/plugin.json` is
  hand-maintained — bump its version on each release.
- `build.py` is **duplicated** from ix-skills. A fix to one copy must be carried over
  to the other.

## 8. What we do NOT do

- No conditional logic, API calls, or side effects in skills — skills are prompts
- No external dependencies in `build.py` except `jsonschema` and `pyyaml`
- No generated files in the repo except `dist/`
- No skill ids with accents or uppercase letters
- No borrowed content without its licence checked and its `THIRD_PARTY.md` entry
